## How Java reaches the database

```text
HTTP request
    → Controller: decode input, run @Valid, obtain session principal
    → Service: check actor, current state, and business rules
    → JPA repository OR JdbcTemplate
    → shared DataSource/Hikari pool
    → H2 locally or PostgreSQL in production
```

`DataSourceConfig` creates the connection pool. A datasource supplies connections; it does not create the schema. Flyway reads the packaged migrations at startup, applies versions not yet recorded, and checks previously applied versions. Hibernate uses `ddl-auto: validate`, so it validates mapped entities rather than generating replacement tables.

Maven copies only `database/migrations/` into `db/migration` in the application. Do not edit an already applied migration to add comments: its stored checksum may no longer match. Make schema changes in a new versioned migration. The `explained/` files are documentation copies, never an alternative migration source.

## Two persistence styles

| Style | Used for | How to read it |
| --- | --- | --- |
| JPA entities and Spring Data repositories | Accounts, profiles, skills, and link tokens | An entity describes a row; annotations map relationships. Spring implements methods such as `findByEmail`. Loaded entities remain managed within a service transaction. |
| `JdbcTemplate` | Account OTP state, marketplace records, wallet records | SQL explicitly selects/inserts/updates rows. Query maps use database column labels, such as `owner_id`. Parameters follow the SQL string rather than being inserted into it. |

Both styles use the shared datasource. Class-level service `@Transactional` normally groups participating work into one transaction. JPA tracks changes to managed entities and flushes them at commit, so a setter/update method may persist even without another repository `save` call. JDBC updates execute explicit statements; their changes still participate in the enclosing transaction.

## IDs that look similar but mean different things

| Column | Meaning |
| --- | --- |
| `users.id` | Application account identity, stored in `StudentPrincipal.id`. |
| `student_profiles.id` | Separate profile row identity. |
| `student_profiles.user_id` | Unique link from a profile to its account. |
| `student_skills.student_id` | References **profile ID**, not account ID. |
| `campus_jobs.owner_id`, `helper_id` | Requester/helper **account IDs**. Helper is null before acceptance. |
| `job_attachments.job_id` | Both the attachment primary key and a foreign key; at most one attachment per job. |
| `wallet_accounts.user_id` | Both wallet primary key and user foreign key; at most one wallet per account. |
| `wallet_transactions.reference_id` | Application-level request reference. It is not a declared foreign key; `kind` determines how Java interprets it. |
| `SPRING_SESSION_ATTRIBUTES.SESSION_PRIMARY_ID` | Internal session primary ID, distinct from the browser-facing `SESSION_ID`. |

## Reading SQL syntax in this project

- `CREATE TABLE` defines a record structure; `ALTER TABLE ... ADD COLUMN` extends an existing one.
- `BIGINT GENERATED BY DEFAULT AS IDENTITY` allocates numeric IDs. Java obtains newly inserted job/request IDs using `GeneratedKeyHolder` rather than guessing them.
- `PRIMARY KEY` identifies each row. A composite primary key identifies a combination, such as `(student_id, skill_id)`.
- `NOT NULL` requires a value. It does not reject blank strings; DTO/service rules do that where required.
- `UNIQUE` prevents duplicate values or combinations even when concurrent requests race past a Java pre-check.
- `DEFAULT` supplies an initial value when an insert omits that column.
- `CHECK` restricts stored values, such as a nonnegative balance or a 1–5 rating. Some status/kind text columns have no database enum/check; Java controls those values.
- `REFERENCES`/`FOREIGN KEY` requires a matching related row. It does not prove the caller is allowed to access that row; Java participant/admin checks remain necessary.
- `ON DELETE CASCADE` removes dependent rows with a deleted parent where explicitly declared. It is not a general permission to delete accounts; other foreign keys can still block deletion.
- `CREATE INDEX` provides an access path for lookups/sorting. It does not guarantee every query will use that index; the database chooses a plan.
- `DECIMAL(p,s)` stores exact decimal values, with total precision `p` and fractional scale `s`. Java uses `BigDecimal` for money.
- `BYTEA` stores binary bytes: documents, proof screenshots, and serialized session attributes.
- `JOIN` requires a matching related row; `LEFT JOIN` retains the main row even without a related one, such as an unassigned helper.
- `AS` gives a result column a readable label, such as `owner_name`.
- `WHERE` limits rows; `ORDER BY ... DESC` chooses newest/highest IDs first; `LIMIT` and `OFFSET` bound a page.
- `?` is a bound parameter. Its Java argument order must match placeholder order; values must not be concatenated into SQL.
- `FOR UPDATE` locks selected existing rows until transaction completion. Other transactions changing the same rows must wait.
- `CASE WHEN` chooses a computed value, used for moderation status changes and pending-first admin ordering.
- `COUNT(*)` counts rows; affected-row counts from `update` let Java distinguish a successful change from a missing/unauthorized target.

## Follow one job through its tables

1. `MarketplaceService.post` inserts `campus_jobs`; the database supplies its ID and initial OPEN status. A Xerox request also inserts `job_attachments` with the generated ID inside the same transaction.
2. `act("accept")` locks the job, checks availability/self-acceptance, assigns `helper_id`, and stores an encoded delivery code plus expiry/attempt state. Java attempts to email the raw code to the requester; SMTP failure no longer rolls back acceptance.
3. The helper starts and advances category-specific manual `progress_step` values. Reaching `AT_BLOCK` marks the job DELIVERED. These rows are manual updates, not location tracking.
4. Participant chat inserts `job_messages`. The service writes a notification for the other participant into `notifications`.
5. The helper enters the requester-shared code after physical receipt. For a DELIVERED job, the authenticated requester may generate a replacement in-app using the same hash/expiry/attempt columns; no raw secret is stored. Wrong codes increment the persisted attempt count. A normal result containing `otp_error` keeps those writes committed; an ordinary runtime exception would roll them back.
6. Valid handoff marks the job COMPLETED and clears the stored hash/expiry. `earnings` sums these completed rewards; `collect` separately records offline reward collection.
7. Participants may insert one review each into `job_reviews`; `UNIQUE(job_id,reviewer_id)` blocks duplicates. Reports go into `job_reports` for administrator handling.

Public job details can include print metadata. Reading the document bytes requires the separate participant-authorized download path. Database foreign keys establish relationships; they do not replace access checks.

## Wallet transactions step by step

### Welcome credit

New registration inserts a `wallet_accounts` row with INR 100 and a positive completed `WELCOME_CREDIT` ledger entry. V5 gives the same one-time starting credit to users who already existed when that migration ran. The backfill must not be rerun manually.

### Top-up

A student pays externally and submits a normalized UTR plus optional proof. The service inserts a PENDING `wallet_topup_requests` row; the balance stays unchanged. The unique UTR prevents submitting the same top-up reference twice.

Admin review locks the request and requires PENDING status. APPROVED adds to balance and inserts a positive completed TOPUP entry; REJECTED adds no credit. Both decisions record the reviewer and timestamp. A repeated review is rejected, so it cannot credit twice.

### Withdrawal

The service locks the wallet balance, verifies available funds, subtracts the requested amount immediately, inserts a PENDING withdrawal, and writes a negative PENDING WITHDRAWAL entry. Those changes share one transaction, so funds cannot be overspent by simultaneous requests.

When the administrator pays externally, PAID records the outgoing UTR and completes the existing debit. It does **not** subtract the amount a second time. REJECTED restores the available balance, marks the debit rejected, and adds a positive completed WITHDRAWAL_REFUND entry. The debit/refund history remains visible.

No gateway automatically moves money. Job rewards are offline earnings and do not automatically settle into this wallet. When interpreting the ledger, consider both signed amount and status; a simple unfiltered sum of every historical row is not a general balance-reconciliation rule.

## Three different account/code stores

| Store | Purpose and lifetime |
| --- | --- |
| `email_verification_tokens`, `password_reset_tokens` | Random single-use **link** secrets. Only SHA-256 hashes are stored, with timestamp expiry and consumption. |
| `email_otps` | Six-digit **account** ownership/recovery state. Local mode stores encoded verifiers; managed mode stores a marker while Neon Auth checks mailbox ownership. Java persists purpose, cooldown, expiry, attempts, and used state. |
| `campus_jobs.completion_otp_*` | **Delivery handoff** verification. Java generates/checks the code; the requester shares it only after receiving the order. |

`OtpService.issue` uses `REQUIRES_NEW`, so its cooldown record commits independently of the surrounding account transaction. `verify` also uses `noRollbackFor = ApiException.class`, so incorrect attempts remain recorded even when verification fails. These are explicit exceptions to the usual service rollback behavior.

PostgreSQL stores records; it does not send these emails. Java calls Neon Auth or the selected `EmailDelivery` implementation. Java owns the application password/session even when a managed provider proves email ownership.

## Shared sessions and revocation

Production enables Spring Session JDBC. `SPRING_SESSION` holds timing/lookup metadata; `SPRING_SESSION_ATTRIBUTES` holds serialized authentication values. Deleting a session cascades to its attributes. Secure HTTP-only cookies carry its identifier.

`StudentPrincipal` snapshots `credentialVersion` at login. `AccountSessionFilter` reloads the user and rejects a different version, inactive/unverified state, or a deleted account. Password changes and admin moderation therefore revoke older sessions through current database state.

## Time columns and local development

V1 JPA account/token columns use `TIMESTAMP(6)` with Java `Instant`. Marketplace/OTP/wallet tables use `VARCHAR(40)` timestamps supplied by Java, generally through `Instant.now().toString()`. V5's existing-user welcome backfill uses `CAST(CURRENT_TIMESTAMP AS VARCHAR)` instead. Read the column definition and insertion code rather than assuming every time is stored identically.

Production uses Neon PostgreSQL. Local development uses persistent H2 in PostgreSQL compatibility mode; tests use isolated in-memory H2. Passing H2 tests checks application behavior but is not a claim that a live production database was exercised.
